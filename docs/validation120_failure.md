# 120更新目の検証失敗

> 設定整理後の実行手順は[最新README](../README.md)を参照してください。学習用YAMLは `training_fast.yaml` と `training_diffusion_scenario.yaml` の2つです。以下には過去の設定名を含む調査・実装時の記録があります。

`mobility_fixed/validation_00120_39202f4eef1e42149a807184c250e67c/` の8候補は、
run=101で正常終了、run=102で全てSIGABRTとなった。
エラーは `Cannot receive DATA while receiving CTRL.`、時刻3.857428569秒、node=25。
候補0を同じ入力・seed・runで1並列再実行しても再現した。
記録は `data/processed/validation120_serial_replay/` に保存している。
当初のPython側修正では未解決だったが、その後NS-3内部の原因を修正した。
最新の原因説明・検証結果・重み引き継ぎ手順は[NS-3内部修正](ns3_inflight_control_fix.md)を参照。

以前は、検証の全候補が無効になると例外で停止し、直前に実行した120更新目の重みを保存していなかった。
既存の `latest.pt` は119更新目、`mobility.pt` の最良検証報酬は0.5。
元チェックポイント、履歴、失敗ログは変更していない。

## 修正

- 検証結果に `complete` / `partial` / `invalid` を記録する。
- 有効候補0件の場合は報酬を `null` とし、0点や成功として扱わない。
- 検証結果を各検証ディレクトリの `summary.json` に保存する。
- 学習途中の不完全な検証では警告し、最新モデルとoptimizerを通常どおり保存する。
- 不完全な検証では最良モデルを置き換えない。成功候補だけの平均でモデルを有利に選ばない。
- 学習開始前の検証が不完全な場合は、基準となるモデルを選べないので停止する。
- 最終metricsには不完全だった検証回数と最後の検証状態も記録する。
- NS-3の異常終了を無視して正常扱いする変更や、乱数条件の差し替えはしていない。

NS-3のビルドが変更されたため、現在は旧チェックポイントの直接resumeではなく、
上記資料の `--initialize-from` を使用する。

## 学習成績について

保存された119更新のうち109更新は平均訓練報酬が+1。
同じ入力の有効候補がすべて+1の場合、leave-one-out baselineとの差が0となり、
その入力からの報酬由来の方策勾配は0になる。
検証平均報酬は0更新0.5、20更新0.5、40更新0.375、60/80/100更新0.0。
訓練成功率の高さだけで改善とは判断できない。報酬設計や潜在表現の改善は別途検討が必要。
今回、報酬定義は変更していない。
