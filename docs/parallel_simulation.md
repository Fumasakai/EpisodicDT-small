# エンコーダ・デコーダ学習の並列実行

> 設定整理後の実行手順は[最新README](../README.md)を参照してください。学習用YAMLは `training_fast.yaml` と `training_diffusion_scenario.yaml` の2つです。以下には過去の設定名を含む調査・実装時の記録があります。

現在は追加のNS-3内部修正を適用済み。既存119更新目の重みを引き継ぐ場合は
[最新の修正と実行手順](ns3_inflight_control_fix.md)を参照してください。

`training.simulation_workers` で同時実行するNS-3プロセス数を指定する。
`configs/pipeline.yaml` と現在の `training_fixed.yaml` には実測比較で選んだ値を設定する。
指定がない既存設定は1並列のまま動く。

1更新の入力2件、候補数4件、合計8候補は変更しない。モデルによる候補生成は
メインスレッドで行い、候補ごとのCSV出力・NS-3実行・イベント判定を並列処理する。
全結果を元の候補順に集約してから、従来と同じ損失で1回更新する。
Pythonのスレッドは外部NS-3プロセスを待機するために使い、モデルの重み更新は並列化しない。

検証時もエピソード単位で同じ並列数を適用する。1エピソードの検証用乱数条件101・102は
そのワーカー内で順番に実行するため、設定した並列数より多くのNS-3プロセスを起動しない。
保存先は候補ごとに独立し、失敗・タイムアウト・判定不能の扱いは従来どおり。
入力が不正な場合などの予期しない例外は握りつぶさない。

## 中断した学習の再開

並列数だけの変更はチェックポイントとの互換性確認で許可する。
モデル、データ、NS-3ビルドなどに対する既存の確認は継続する。

```bash
OMP_NUM_THREADS=1 python -m src.train.train_mobility \
  --config data/processed/training_dataset_next/training_fixed.yaml --resume
```

既存の学習出力がない場合は `--resume` を付けずに新規開始する。
実行中のプロセスにはファイル変更は自動反映されない。

## 比較の方法

停止原因の回帰検証で用いた同じ8候補（24UE、13秒、seed=42、run=1）を使う。
通常学習と合わせてパケット診断を無効にし、4→8→8→4並列の順序で各2回実行する。
候補入力、NS-3の乱数条件、実行バイナリを維持し、全候補終了までの実時間を比較する。
最終的な並列数は各2回の中央値が小さい方を選ぶ。
各候補のKPI、近隣基地局測定、HOイベントCSVのSHA-256が全試行で一致することも確認する。

測定時には別のモデル学習プロセスは稼働していなかった。
CPU・メモリ情報、入力ハッシュ、バイナリハッシュ、実行コマンド、ログ、試行結果は
`data/processed/ns3_parallel_benchmark/` に保存する。
今回の8候補には特に時間のかかる候補が含まれるため、結果は他の候補集合の速度を保証するものではない。

再計測する場合は新しい保存先を指定する。

```bash
OMP_NUM_THREADS=1 python -m src.simulation.benchmark_parallel \
  --source data/processed/ns3_training_regression_fixed \
  --output data/processed/ns3_parallel_benchmark_next
```

この比較時点の対象はエンコーダ・デコーダの学習と検証。現在は[拡散モデルの並列評価](diffusion_speed.md)も追加済み。

## 測定結果

| 並列数 | 1回目 | 2回目 | 中央値 |
|---|---:|---:|---:|
| 4 | 89.04秒 | 88.87秒 | 88.96秒 |
| 8 | 72.56秒 | 72.52秒 | 72.54秒 |

8並列は4並列より約18.5%短縮したため、`simulation_workers: 8` を採用した。
全4試行で、候補ごとのKPI・近隣測定・HOイベントCSVのハッシュが一致した。
